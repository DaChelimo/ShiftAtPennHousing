### [P0] A worker claims and is given a break shift at a house that is closed for the break

**Journey**: Winter break or any break where the admin marks a house closed. The worker opens the
break calendar during the claim window, drags a range, and is told they hold those hours.

**Trigger** (reproduced against the local stack, 2026-07-26):

1. Admin authors a break and sets house X closed for the break (empty band list for the day type).
   `apply_compiled_break` calls `reconcile_config_blocks`, which voids X's future blocks in the
   window: it DELETEs their vacant seats, sets occupied seats to `cancelled_config`, and stamps
   `shift_blocks.voided_at`
   (`supabase/migrations/20260709000004_break_compiler_apply.sql:60-137`).
2. At T-14d the `break-phase-transitions` cron runs `execute_due_break_transitions` ->
   `clear_break_period` -> `open_break_claim_calendar(break, house)` for **every** house that has
   blocks in the break date range, including the closed one.
3. `open_break_claim_calendar`'s UPDATE has no status filter and no `voided_at IS NULL` guard, so
   it flips those `cancelled_config` rows back to `status = 'vacant'`
   (`supabase/migrations/20260531000002_phase_11_break_claim.sql:156-170`).
4. `break_claim_calendar_pool` (same file, line 176) has no `voided_at` guard either, so the seat
   is offered on the calendar.
5. `claim_break_blocks` has no `voided_at` guard, so the drag claims it
   (`supabase/migrations/20260726000009_seat_write_compare_and_swap.sql:1053-1180`).

Runtime transcript (service role, fixtures under the `ccc0...` uuid space, torn down by exact PK):

```
state after the admin closed harrison for this break:
  block voided_at=2026-07-26 23:46:23  seat=cancelled_config
T-14d cron step (clear_break_period -> open_break_claim_calendar):
  cleared = 1
  block voided_at=2026-07-26 23:46:23  seat=vacant        <- resurrected on a VOIDED block
does the break calendar pool now offer this seat on a CLOSED house?
  break_claim_calendar_pool rows = 1
can a worker CLAIM it?
  claim_break_blocks returned: ccc00003-0000-4000-8000-000000000001
  seat AFTER = claimed user=ccc00001-...  block voided_at=2026-07-26 23:46:23
```

**Observed**: The worker holds a `claimed` assignment on a block the config engine retired. The
desk is closed. Nobody will be there to hand over, the door is locked, and the block is invisible
to the orchestrator scan and to `is_assignment_claimable` (both of which do carry the
`voided_at IS NULL` guard), so no escalation and no correction ever fires for it. The worker shows
up and works nothing, or shows up and cannot get in.

**Expected**: A voided block is inert. `supabase/AGENTS.md` ("Operating seasons") states that
voiding a block "makes voided blocks self-excluding on status-filtered reads" and that the
orchestrator scan, `is_assignment_claimable` and both house grids carry an explicit
`voided_at IS NULL` guard as defense in depth. The break path violates the premise that guard
rests on: it is the one path in the product that manufactures a vacant seat on a voided block.
This also directly answers the open question left in the adjacent slice's report
(`docs/qa/qa-open-shifts-claim-2026-07-26.md:645-650`, "I looked for a path that recreates a
vacant seat on a voided block and did not find one inside this slice").

**Blast radius**: Every break where any house is closed. Winter break closes 12 of the 13 houses
by design (BSpec section 2, "During winter break, all houses other than Harnwell are completely
inactive"), so this is the winter-break default, not an edge case. Every worker at a closed house
whose school-year schedule had an assignment in the break window gets at least one resurrected
seat offered to them.

**Fix sketch**:

- `supabase/migrations/20260531000002_phase_11_break_claim.sql` `open_break_claim_calendar`: add
  `AND sb.voided_at IS NULL` to both the count and the UPDATE, and restrict the UPDATE to the
  occupied statuses so it never rewrites `cancelled_config`.
- Same file, `break_claim_calendar_pool`: add `AND sb.voided_at IS NULL`.
- `claim_break_blocks` (currently owned by `20260726000009`): add
  `CONTINUE WHEN v_block.voided_at IS NOT NULL` alongside the existing phase and Harnwell guards,
  and select `voided_at` in the driving `FOR` loop.
- Ship all three in one new migration; the pool and the claim guards are the load-bearing pair
  because the opener is not the only way a stale seat could appear.

**Acceptance check**: pgTAP in `supabase/tests/break-range-claim.sql`: void a block inside a break
window with one `cancelled_config` occupant, call `open_break_claim_calendar`, assert the seat is
still `cancelled_config`, assert `break_claim_calendar_pool` returns zero rows for it, and assert
`claim_break_blocks` over that block returns zero rows. Revert each guard one at a time and watch
the corresponding assertion go red before trusting green.

**Confidence**: verified in code and reproduced at runtime with a verified side effect.

### [P0] After a second break drag, the calendar shows shifts the worker still holds as open, and the hours meter under-reports

**Journey**: A worker claims break hours over more than one sitting, which is the normal shape of a
multi-day break (Monday first, then Tuesday).

**Trigger**:

1. During the claim window the worker drags Monday 16:00 to 18:00. The server claims 4 blocks and
   returns their 4 assignment ids. The host calls
   `breakCalendarVm.reconcileClaim(result.claimedAssignmentIds)`
   (`apps/mobile/androidApp/src/main/java/com/pennhousing/shift/MainActivity.kt:788-808`;
   iOS `apps/mobile/iosApp/iosApp/ContentView.swift:704-712`).
2. Without leaving the screen, the worker drags Tuesday 16:00 to 18:00. The server returns
   Tuesday's 4 ids only.
3. `reconcileBreakClaim` reverts **every** seat where
   `seat.userId == snapshot.meUserId && seat.status.equals("claimed", true) && seat.id !in claimedAssignmentIds`
   (`apps/mobile/shared/src/commonMain/kotlin/com/pennhousing/shift/shared/breakclaim/BreakCalendar.kt:623-641`).
   Monday's 4 seats satisfy that predicate, so they are set back to
   `status = "vacant", userId = null, workerName = null`.

**Observed**: Monday 16:00 to 18:00 renders as open, claimable space. The
`BreakCalendarSnapshot.claimedHours()` sum (same file, line 100) drops by 2 hours, so the
"This week, Xh / 40h" meter under-reports, and `planBreakDrag`'s cap trimming
(`BreakCalendar.kt:444`, `held = snapshot.claimedHours()`) budgets from the wrong number.

Nothing repairs it. The success branch of the host calls `reconcileClaim` and
`repo.refresh.request()` but does **not** bump `revertKey`, and `liveBreakCalendar` is keyed on
`(liveBreak, session.userId, revertKey)` only
(`MainActivity.kt:602`), so `repo.refresh` does not re-fetch the break calendar. The corrupted
snapshot is what the worker looks at until they leave and re-enter the screen.

The follow-on is worse than the display. Seeing Monday apparently open, the worker drags it again.
`claim_break_blocks` refuses every block on the caller time-conflict check (they already hold that
block start), returns an empty set, and the host takes the empty branch and toasts
"Couldn't claim those break shifts. The sign-up window may be closed, or they were just taken."
That statement is false: the window is open and nobody took them, the worker already has them.

**Expected**: The reconcile must revert only the seats **this drag** optimistically flipped. The
worker is never told something false about their own schedule (BSpec section 4.4, "it never
silently claims a different range than the worker sees").

**Blast radius**: Both platforms, identical shared code. Every worker who makes more than one drag
in a session, which is the expected interaction for any break longer than one day. The existing
unit test pins the wrong behavior:
`apps/mobile/shared/src/commonTest/.../breakclaim/BreakCalendarTest.kt:234` reconciles a snapshot
where the only claimed seats are the optimistic ones, so it cannot see this.

**Fix sketch**: `BreakCalendar.kt` `reconcileBreakClaim` needs the set of seat ids the optimistic
apply actually flipped. Either have `applyBreakDrag` return them (change the signature to return
the snapshot plus the flipped ids) and pass them through `BreakCalendarViewModel.commitDrag` ->
`reconcileClaim`, or scope the revert to the block ids of the drag that is being reconciled. Do not
"fix" it by refetching in the host; the pure function is wrong and both platforms consume it.

**Acceptance check**: New case in `BreakCalendarTest.kt`: a snapshot where the worker already holds
seat `b0-s0` as `claimed` from a previous session, optimistically claim `b1-s0`, reconcile with
`setOf("b1-s0")`, assert `b0-s0` is still the worker's and `claimedHours()` is 1.0, not 0.5. Revert
the fix and watch it go red.

**Confidence**: verified in code.

### [P0] Anyone holding the public anon key can claim break shifts as any worker, wipe a house's claimed break shifts, and shut the claim window

**Journey**: Not a worker journey. This is the entire break lifecycle being drivable without a
login.

Same root cause as the already-ticketed anon-execute class in
`docs/qa/qa-open-shifts-claim-2026-07-26.md` (Supabase's default `anon` / `authenticated`
`EXECUTE` grants survive `REVOKE ... FROM PUBLIC`). I am filing it because none of these functions
are in that ticket's enumerated set, and two of them are **destructive** rather than
impersonating: they mass-vacate real workers' claimed shifts and force the break state machine.

**Trigger** (reproduced 2026-07-26; identity established inside the same command, negative control
asserted, every claim turns on a verified side effect):

```
token payload presented on every call: {"iss":"supabase-demo","role":"anon","exp":1983812996}

NEGATIVE CONTROL (author_break_period is anon=f in the catalog)
  POST /rest/v1/rpc/author_break_period            -> HTTP 401

A. claim on behalf of another worker
  seat BEFORE: vacant user=-
  POST /rest/v1/rpc/claim_break_blocks
    {"p_block_ids":["<block>"],"p_user_id":"<any worker>","p_as_of":"2029-11-09T17:00:00Z"}
  -> [{"claimed_block_id":"...","claimed_assignment_id":"..."}]
  seat AFTER : claimed user=bbb00001-0000-4000-8000-00000000000a

B. p_as_of is caller-supplied, so the T-14d..T-1d window is decoration
  real phase at the true wall clock (2026-07-26) for a 2029-11-16 break: pre_open
  same call with p_as_of forged to 2029-11-09 -> claimed anyway
  seat AFTER : claimed user=bbb00001-0000-4000-8000-00000000000a

C. mass-vacate a house's break assignments
  S2 BEFORE: claimed user=bbb00001-...-00000000000e   (a real worker's claimed break shift)
  POST /rest/v1/rpc/open_break_claim_calendar {"p_break_id":"...","p_house_id":"harrison"}
  -> 2
  S2 AFTER : vacant user=-

D. shut the claim window early
  POST /rest/v1/rpc/close_break_claim_pool {"p_break_id":"..."}  -> 1
  break_periods.claim_pool_closed_at = 2026-07-26 23:45:32
```

**Observed**: Live catalog:

```
proname                        prosecdef  anon EXECUTE  authenticated EXECUTE
claim_break_blocks             t          t             t
open_break_claim_calendar      t          t             t
clear_break_period             t          t             t
close_break_claim_pool         t          t             t
send_break_nag                 t          t             t
execute_due_break_transitions  t          t             t
break_claim_calendar_pool      t          t             t
break_claim_phase              t          t             t
author_break_period            t          f             t
remove_break_period            t          f             t
apply_compiled_break           t          f             t
```

`supabase/migrations/20260615000001_break_calendar_drag_claim.sql:192-193` does
`REVOKE ALL ON FUNCTION claim_break_blocks(...) FROM PUBLIC; GRANT EXECUTE ... TO service_role;`
which, per `supabase/AGENTS.md`, does not strip the default per-role grants.
`20260531000002_phase_11_break_claim.sql:509-527` does the identical PUBLIC-only revoke for the
five lifecycle functions. `20260726000009` re-creates `claim_break_blocks` and does not add a
named revoke either.

Two break-specific harms on top of the impersonation:

- `claim_break_blocks` derives its clock entirely from `p_as_of`
  (`20260726000009:1107`, `break_claim_phase(v_break_id, p_as_of) <> 'claim_window'`). The
  `break-claim` Edge Function stamps `new Date().toISOString()` server-side
  (`supabase/functions/break-claim/index.ts:113`), but nothing forces a caller through it. The
  entire T-14d to T-1d window is therefore advisory against a direct REST call.
- `open_break_claim_calendar` is a mass DELETE-equivalent: it sets every non-vacant assignment in
  the break range at a house to `vacant` with no authorization check whatsoever, and emits no
  notification, so the affected workers are never told.

`break_claim_calendar_pool` being `anon`-readable additionally lets an unauthenticated caller
enumerate every vacant break seat at every house.

**Expected**: `supabase/AGENTS.md`: "A function meant to be service-role-only needs
`REVOKE EXECUTE ON FUNCTION <fn> FROM anon, authenticated;` naming those roles explicitly, in the
same migration that creates or changes it."

**Blast radius**: Anyone with the mobile or web bundle. The destructive path (C) can void an entire
house's break coverage in one unauthenticated request.

**Fix sketch**: One migration that, for `claim_break_blocks`, `open_break_claim_calendar`,
`clear_break_period`, `close_break_claim_pool`, `send_break_nag`, `execute_due_break_transitions`
and `break_claim_calendar_pool`, issues
`REVOKE EXECUTE ON FUNCTION <fn>(<sig>) FROM anon, authenticated;` naming the roles. Separately,
`claim_break_blocks` should derive the actor from `COALESCE(auth.uid(), p_user_id)` the way
`author_break_period` and `apply_compiled_break` already do
(`20260709000001:60-66`, `20260709000004:588-592`), and should clamp `p_as_of` to `app_now()` for
non-service callers so the claim window is not caller-controlled.

**Acceptance check**: A pgTAP grant assertion naming `anon` and `authenticated` explicitly for each
function (`has_function_privilege('anon', ...)` and `has_function_privilege('authenticated', ...)`
both false). Then re-run the probe transcript above and require HTTP 401 on every call, with the
target rows unmutated.

**Confidence**: verified in code and reproduced at runtime with verified side effects, an
established identity, and a passing negative control.

### [P1] At T-14d every worker's break-week shifts are deleted and nobody is told

**Journey**: A worker with a normal school-year schedule that runs into the break week. They check
My Shifts a few days later and their break-week shifts are gone.

**Trigger**: The `break-phase-transitions` cron fires at T-14d ->
`execute_due_break_transitions` -> `clear_break_period` -> `open_break_claim_calendar`. The UPDATE
at `supabase/migrations/20260531000002_phase_11_break_claim.sql:156-170` sets every non-vacant
assignment in the range to `vacant`, `user_id = NULL`. There is no `INSERT INTO notifications` in
that function, nor in `clear_break_period` (line 345), nor in `execute_due_break_transitions`
(line 471).

**Observed**: The worker's assignments disappear with no in-app entry and no push. Compare the
config path, which does emit: `reconcile_config_blocks` inserts a `personal_shift` notification
with `kind = 'shift_cancelled_config'` for every occupant it cancels
(`supabase/migrations/20260709000004_break_compiler_apply.sql:66-74` and `195-201`). The break
clear is the same event and is silent.

**Expected**: BSpec section 10.1: "Personal notifications (your own shift was dropped, you've been
assigned a float, your acknowledgment is overdue) are sent immediately to the affected worker.
These notifications are mandatory and cannot be silenced." Losing your scheduled shifts to the
break clear is a personal shift change.

**Blast radius**: Every worker at every open house, every break. The only other signal is the T-3d
nag, which is itself content-free (see the next ticket), so the practical experience is that the
schedule empties and the app says nothing meaningful about it for 11 days.

**Fix sketch**: In `open_break_claim_calendar`, before the UPDATE, insert one `personal_shift`
notification per distinct (user, break) with a payload carrying `kind`, an explicit `title` and
`body`, and the break id, mirroring the `shift_cancelled_config` shape. One row per worker per
break, not per block, or the inbox floods.

**Acceptance check**: pgTAP: seed a worker with N scheduled assignments inside a break window, run
`clear_break_period`, assert exactly one notification row for that worker with a non-empty
`payload->>'title'` and `payload->>'body'`.

**Confidence**: verified in code.

### [P1] The admin break preview says "exactly what will change" while omitting the wipe of every existing assignment, and nothing stops a break authored inside its own claim window

**Journey**: An admin declares a break on the `/admin/breaks` screen, previews the impact, sees a
small number, and applies.

**Trigger**:

1. Author a break whose per-house headcount and hours match the school-year config (the common
   case: the break just changes the scheduling mode, not the staffing).
2. Click "Preview changes". `previewOrApplyBreak(input, true)` calls `apply_compiled_break` in
   dry-run, whose counters come entirely from `reconcile_config_blocks`
   (`apps/web/lib/actions/breaks.ts:76-83`). That function only cancels occupants when the target
   headcount is 0 (void) or lower than current
   (`supabase/migrations/20260709000004_break_compiler_apply.sql:63` and `:169-175`). With matching
   config neither branch fires, so `assignments_cancelled = 0` and `affected_workers = []`.
3. Apply. At T-14d `clear_break_period` vacates **every** assignment in the window
   (`20260531000002:156`).

**Observed**: The screen renders "Preview shows exactly what will change (shifts created, workers
affected) before ..." (`apps/web/components/breaks/BreakAuthoring.tsx:519`) next to a
zero. The `willVoid` confirmation gate is derived from those same counters
(`BreakAuthoring.tsx:251`), so the admin is not even asked to confirm. The single largest
consequence of declaring a break is invisible in its own preview.

Second half, same surface: the only date validation is
`name.trim() !== '' && startDate !== '' && endDate !== '' && startDate <= endDate`
(`BreakAuthoring.tsx:249`), and `compileBreak` validates format and ordering only
(`packages/core/src/break-authoring/index.ts:139-150`). Nothing requires a start date more than 14
days out, or even in the future. A break authored with `startDate = today + 1` is immediately past
both `open_at` and `close_at` (offsets `-14 days` and `-1 days`,
`packages/core/src/break-authoring/index.ts:21-25`), so on the next 15-minute cron tick
`execute_due_break_transitions` clears every assignment in the window **and** closes the pool in
the same run: the calendar picker never opens for anybody, and every seat lands in the open feed
unclaimed.

**Expected**: BSpec section 4.4 describes a T-14d to T-1d claim window as the mechanism by which
break coverage happens. A break that cannot have one should be refused or loudly warned, and the
preview copy must not claim completeness it does not have.

**Blast radius**: Every break authored with matching staffing (the majority) under-reports; every
short-notice break silently skips round 1 entirely. One admin action, campus-wide effect.

**Fix sketch**:

- `supabase/migrations/20260709000004_break_compiler_apply.sql`: have `apply_compiled_break` count
  the assignments the T-14d clear will vacate (occupied assignments on future blocks in the window)
  and return them as a distinct impact field, and surface it in `BreakImpact` in
  `apps/web/lib/actions/breaks.ts` and in the `ImpactGrid` in `BreakAuthoring.tsx`. Fold it into
  `willVoid` so the confirm gate fires.
- `BreakAuthoring.tsx`: block or hard-warn when `startDate` is fewer than 15 days out, naming the
  consequence ("the sign-up window will not open, shifts go straight to open shifts").
- Re-word line 519 so it does not promise exactness the counters do not deliver.

**Acceptance check**: A Vitest or Playwright case asserting the preview for a same-staffing break
over a window containing K occupied assignments reports K, not 0. A form test asserting apply is
blocked or gated for `startDate < today + 15`.

**Confidence**: verified in code (the counter branches and the validation predicate are both
read directly; the T-14d clear is verified at runtime in the P0 above).

### [P1] The web break board silently drops the last hour of the final day of every winter-time break

**Journey**: A worker using the web portal (`/home/breaks`) during the claim window for
Thanksgiving or winter break.

**Trigger**: `getWorkerBreakBoard` builds its window with hardcoded UTC offsets:

```ts
const windowStart = new Date(`${brk.start_date}T00:00:00-05:00`);
const windowEnd = new Date(`${brk.end_date}T23:59:59-04:00`);
```

(`apps/web/lib/data/worker/breaks.ts:128-129`), then filters
`house_schedule_grid` with `.lte('start_at', windowEnd.toISOString())` (line 136).

Worked example, Thanksgiving 2026 (Nov 25 to Nov 29, America/New_York is EST, UTC-5 throughout):
`2026-11-29T23:59:59-04:00` is `2026-11-30T03:59:59Z`, which is **2026-11-29 22:59:59 EST**. The
`lte` filter therefore excludes every block starting at 23:00 and 23:30 NY on the last day of the
break.

**Observed**: Two 30-minute blocks per seat on the final break day never appear on the web board.
They are not claimable, and they are not visible as coverage that needs filling. The break profile
runs to `shift_end_bound = '00:00'` (24:00), so those are real staffed blocks.

The same asymmetry bites the other way for a summer-time break: `T00:00:00-05:00` resolves to
01:00 EDT, so a break whose houses open at 00:00 would lose its first hour. With the current
08:00 start bound that half is inert today, but it is the same defect.

Mobile does this correctly:
`LocalDateTime(startDate, LocalTime(0,0)).toInstant(NEW_YORK)` and
`endDate.plus(1, DAY)` at NY midnight exclusive
(`apps/mobile/shared/.../data/WorkerShiftsRepository.kt:704-706`). So web and mobile disagree about
what the break window contains, silently, by construction.

**Expected**: AGENTS.md hard invariant 6: "all timestamps are `timestamptz` in America/New_York.
Never use naive timestamps. Never do wall-clock arithmetic for DST-crossing intervals." A literal
`-05:00` / `-04:00` is a naive timestamp wearing an offset.

**Blast radius**: Every web-portal worker, every EST break (Thanksgiving, winter break, and any
short break between the November and March DST transitions). One hour per seat per break, and a
silent divergence from the mobile view of the same break.

**Fix sketch**: In `apps/web/lib/data/worker/breaks.ts`, build the window the same way the file
already builds NY calendar dates elsewhere (it has an `Intl.DateTimeFormat` NY helper at line 49):
resolve NY midnight of `start_date` and NY midnight of `end_date + 1 day` as instants, and filter
with `gte(start)` / `lt(endExclusive)`. Do not hand-write offsets anywhere in this file.

**Acceptance check**: A Vitest case over `getWorkerBreakBoard`'s window computation with
`start_date = '2026-11-25'`, `end_date = '2026-11-29'` asserting the window includes a block at
`2026-11-29 23:30` NY, plus a mirror case for an EDT break. Revert the fix and watch it go red.

**Confidence**: verified in code (the offsets are literal and the arithmetic is closed-form).

### [P1] One float commitment inside a break window stops the break lifecycle for every break, forever

**Journey**: Nobody's. This is a cron path with no user present, which is why nobody would find out.

**Trigger**:

1. A break window contains at least one assignment with `parent_float_id IS NOT NULL` or status in
   `('pending_float_in','pending_float_out','floated_in','floated_out')` at some house. Reachable
   when a break is authored or extended over dates already inside the escalation horizon (a
   short-notice break, or an edit that pulls the start date earlier), or after a force-triggered
   float into a break-window block. `parent_float_id` is never cleared once set.
2. The `break-phase-transitions` cron (`*/15 * * * *`) runs `execute_due_break_transitions`.

**Observed**, reproduced live:

```
picked house=harnwell date=2026-07-25
now clear_break_period (the T-14d cron step):
ERROR:  break_clear_float_commitment_requires_manual_override
CONTEXT: PL/pgSQL function open_break_claim_calendar(uuid,text) line 19 at RAISE
         PL/pgSQL function clear_break_period(uuid) line 24 at assignment
```

`open_break_claim_calendar` raises at
`supabase/migrations/20260531000002_phase_11_break_claim.sql:142`. Neither `clear_break_period`
(line 345) nor `execute_due_break_transitions` (line 471) has an `EXCEPTION` block, so the raise
propagates out of the cron statement and aborts the whole transaction. Three consequences:

- The `break_phase_log` row `clear_break_period` inserted first is rolled back, so it retries and
  fails identically every 15 minutes forever.
- The `FOR` loop in `execute_due_break_transitions` aborts, so **every other break** in the same
  run is skipped: no calendar opens, no T-3d nag fires, no pool closes.
- Nothing surfaces the failure to a human. There is no alert on a failing cron.

**Expected**: A blocked house is a per-house condition and should not take down the campus-wide
transition engine, and it should reach an admin rather than a Postgres log.

**Blast radius**: All breaks, all houses, once triggered. The failure is total and silent: workers
see a calendar that never opens and get no nag; the pool never closes, so leftovers never reach the
open feed either.

**Fix sketch**: In `clear_break_period`, wrap the per-house `open_break_claim_calendar` call in a
`BEGIN ... EXCEPTION WHEN OTHERS` so one blocked house is recorded (a notification to the project
administrator, or a row in `break_phase_log` with a `blocked` phase) and the loop continues. In
`execute_due_break_transitions`, wrap each break's three steps the same way so one break cannot
starve the rest.

**Acceptance check**: pgTAP: two due breaks, plant a `pending_float_in` inside break A's window,
call `execute_due_break_transitions`, assert break B is cleared and that break A produced a
recorded blocked outcome rather than an exception.

**Confidence**: verified in code, and the raise reproduced live. Reachability of the precondition
is inferred from the authoring surface (no minimum lead time, see the preview ticket).

### [P1] Mobile tells the worker nothing when the server trims a break drag

**Journey**: FCFS. Two workers drag overlapping ranges at the same instant. One of them gets part
of what they dragged.

**Trigger**:

1. Worker drags 16:00 to 20:00 (8 blocks). The action bar previews "Claimed 16:00 to 20:00".
2. They tap Claim. `commitDrag` optimistically flips all 8 and stores
   `lastMessage = plan.message`
   (`apps/mobile/shared/.../viewmodel/BreakCalendarViewModel.kt:134`).
3. The server returns 3 seats (the other 5 were taken, or trimmed by the hard cap, or Harnwell).
4. `reconcileClaim` folds in the 3 and does not touch `lastMessage`
   (`BreakCalendarViewModel.kt:140-143`).

**Observed**: `BreakCalendarUiState.lastMessage` is never rendered by either front end
(grep-confirmed across `apps/mobile`; the only message shown is `plan.message` in the pre-claim
action bar, `apps/mobile/androidApp/.../ui/BreakCalendarScreen.kt:591` and
`apps/mobile/iosApp/iosApp/BreakCalendarView.swift:443`). So after a partial claim the worker gets
**no message at all**. The grid changes under them and the difference between "I got 4 hours" and
"I got 90 minutes" is something they have to notice by re-reading the calendar. Total failure is
messaged; partial success is not.

Web is better but incomplete: it reports the server-trimmed count,
`Claimed ${res.claimed} shift${...}` (`apps/web/components/worker/BreakClaim.tsx:105`), which is
true. It does not say which part was taken, and it calls a 30-minute block a "shift", so an 8-block
claim reads "Claimed 8 shifts."

**Expected**: BSpec section 4.4 is explicit: "blocks that filled up first (or that the worker
already covers) are trimmed away, and the worker is told which part was taken and which was already
full (e.g. 'Claimed 4:00 to 6:00; 6:00 to 8:00 was already full'). ... it never silently claims a
different range than the worker sees."

**Blast radius**: Every partial break claim on both mobile platforms. FCFS is the whole design of
this surface, so partial claims are the expected outcome, not the exception.

**Fix sketch**: `BreakCalendarViewModel.reconcileClaim` should recompute the message from the
server's actual result (claimed segments from the returned assignment ids, trimmed segments from
the difference against `plan.claimableBlockIds`) using the existing `dragMessage` helper in
`BreakCalendar.kt:555-572`, then both hosts must render `uiState.lastMessage` as a toast. Reuse
`WriteFeedback`'s partial-claim tone so a partial claim is not shown as a red failure, per the
existing convention.

**Acceptance check**: `BreakCalendarTest` case: plan 8 blocks, reconcile with 3 assignment ids,
assert the resulting message names the claimed range and the trimmed range. A Compose/XCUITest
assertion that the toast appears after a partial claim.

**Confidence**: verified in code.

### [P2] Under the simulated clock the web break board and the break-claim write disagree about which phase the break is in

**Journey**: A demo or a staging walkthrough with the sim clock offset, which is how this product
is shown to stakeholders and how break timing is exercised at all (the local clock is currently
offset by about 28 hours: `now()` 2026-07-26 23:43Z vs `app_now()` 2026-07-25 14:29Z).

**Trigger**: Set the sim clock so a break is inside its claim window by `app_now()` but not by the
real clock. Open `/home/breaks` and claim.

**Observed**: The web page computes the phase with `simNow()`
(`apps/web/app/(worker)/home/breaks/page.tsx:14` and
`apps/web/lib/data/worker/breaks.ts:110-113`) and renders the banner "Claim window is open"
(`apps/web/components/worker/BreakClaim.tsx:20-24`). The write goes to `break-claim`, which stamps

The cron side uses `app_now()` (`execute_due_break_transitions`, verified in the live catalog),

**Fix sketch**: Have the `break-claim` Edge Function pass `app_now()` rather than `new Date()`, or
have `claim_break_blocks` default `p_as_of` to `app_now()` and ignore the parameter for non-service
callers (which also closes the forged-window half of P0-3). Then make the empty-result copy name
the real reasons rather than asserting "just taken".

**Acceptance check**: With `allow_time_travel = true` and the clock offset into a break's claim
window, a claim from `/home/breaks` succeeds. With the clock outside the window, the message says
the window is closed rather than "just taken".

**Confidence**: verified in code (both clock sources read directly, offset measured live). The
end-to-end user-visible sequence is needs-runtime-check; I did not drive the web UI.

## Verified clean

Each of these I actively tried to break and could not, with the guard that stops it.

- **The FCFS race on `claim_break_blocks` is genuinely safe.** This was the headline risk and it
  holds. `claim_break_blocks` picks its seat per block with
  `ORDER BY a.assignment_id FOR UPDATE SKIP LOCKED LIMIT 1`
  (`supabase/migrations/20260726000009_seat_write_compare_and_swap.sql:1148-1160`) and repeats the
  predicate on the write (`WHERE assignment_id = v_seat AND status = 'vacant'`), so a loser is
  trimmed rather than overwriting the winner. It also takes `users FOR UPDATE` on the claimer
  before the seat, matching the global lock order in `supabase/AGENTS.md`, so one worker's two
  simultaneous drags cannot both pass the time-conflict and cap checks.

  Proven with two overlapping sessions, not two `&`-launched processes hoping to collide. Six
  rounds, both sessions parked on a shared server-side wall-clock barrier, with entry and exit
  timestamps printed to establish the overlap. Round 1 is representative: A entered at
  `23:43:52.848490` and exited at `23:43:52.964492`; B entered at `23:43:52.849004`, inside A's
  execution, and exited at `23:43:52.975595`. Across all six rounds the one-seat block ended with
  exactly **1** claimed seat and the loser returned an empty set. Script kept at
  `/private/tmp/.../scratchpad/break-race.sh`; fixtures under the `bbb0...` uuid space, torn down
  by exact primary key.

- **Per-block seat allocation.** The drag sends block ids, not assignment ids, on both clients and
  on web: mobile `commitDrag` returns `plan.claimableBlockIds` and the host POSTs `block_ids`
  (`MainActivity.kt:788`, `ContentView.swift:704`); web posts `block_ids` too
  (`apps/web/lib/actions/worker/breaks.ts:20-23`). The Edge Function validates every element is a
  uuid and routes to `claim_break_blocks`
  (`supabase/functions/break-claim/index.ts:104-127`). There is no representative-seat id anywhere
  on this path, so the "N open card carries one seat" failure shape does not exist here. Web and
  mobile do not diverge on the payload.

- **Block atomicity.** The drag is index-based over `day.blocks`, each of which is one 30-minute
  block; `planBreakDrag` tags every block individually and returns a block-id list
  (`BreakCalendar.kt:430-531`). The server iterates
  `WHERE sb.block_id = ANY (p_block_ids) ORDER BY sb.block_start_at, sb.block_id` and claims one
  seat per block. No range is ever sent or stored.

- **Claim-window anchoring is on the break start date and is DST-correct.** `break_claim_phase`
  computes `(bp.start_date::timestamp + op.claim_phase_open_offset) AT TIME ZONE 'America/New_York'`
  (live catalog, source `20260531000002:64-83`). The interval is added to a **naive** timestamp,
  which is calendar-day arithmetic, and only then localised, so T-14d is exactly NY midnight
  fourteen calendar days before the start date whether or not a DST transition falls in between.
  It anchors on `bp.start_date`, never on the block's own date, so all dates in the break share one
  boundary as BSpec section 4.4 requires. A NULL `p_as_of` falls through the CASE to `open_feed`,
  which fails closed (no claim), not open. The TypeScript mirror
  (`packages/core/src/break-claim/index.ts:21-49`) does the same thing by a different route (UTC
  date arithmetic then `fromZonedTime`) and agrees; it is currently unreferenced outside its own
  tests, so there is no live drift.

- **Harnwell training at the break write point.** `claim_break_blocks` carries
  `CONTINUE WHEN v_block.house_id = 'harnwell' AND v_claimer.home_house_id <> 'harnwell'`
  (`20260726000009:1110`), it is enforced at the write and not inherited from the feed, and there
  is a table-level backstop trigger `shift_block_assignments_enforce_harnwell_training` confirmed
  present on `shift_block_assignments` in the live catalog. The break calendar read is also scoped
  to the worker's own `home_house_id` on both clients.

- **The weekly hours cap does apply to break claims, incrementally, and trims the tail.**
  `claim_break_blocks` re-reads the worker's occupied block count per iteration inside the loop, so
  rows claimed earlier in the same drag are counted, and `effective_weekly_cap(week_start,
block_start)` resolves the week's cap including HM/BM overrides
  (`20260726000009:1113-1140`). Break hours are additional hours and the cap is checked, unlike
  floats (AGENTS.md invariant 4, which is float-only). The week boundary is
  `date_trunc('week', block_start AT TIME ZONE 'America/New_York')` converted back through
  `AT TIME ZONE`, which is the DST-safe form.

- **Claim-window leakage into the open feed.** `worker_open_shifts` excludes any block whose NY
  date falls in a break period whose phase is not `open_feed`, so a break seat, including one
  dropped back during the window, does not appear in the weekly feed until T-1d. Verified in the
  live view definition (`weekly_visible` CTE) and consistent with BSpec section 4.4 ("During the
  claim phase, break shifts do not appear in the open-shifts feed").

- **The break tour cannot fire a real claim.** `BreakTour` renders an entirely synthetic grid:
  fixed `SAMPLE_BLOCK_COUNT = 6`, fixed `TAKEN_SEATS`, fixed lane labels, no block ids
  (`apps/mobile/shared/.../onboarding/BreakTour.kt:44-80`). The interactive steps mutate only local
  `selFrom` / `selTo` / `selLane` state
  (`apps/mobile/androidApp/.../ui/onboarding/BreakTourView.kt:98-140`); there is no path from the
  tour into `BreakCalendarViewModel` or `WorkerShiftsRepository`. The tap-outside dismiss is gated
  to the non-drag step (`dismissible = step.id == BreakTourStepId.LAYOUT`,
  `BreakTourView.kt:95`), matching the AGENTS.md note that CLAIM and DROP both protect a real
  press-and-drag. See "Not checked" for the one residual I could not close from source.

- **Double submit.** Web disables the claim button on `busy`
  (`BreakClaim.tsx:190`). Mobile is protected structurally: a second drag over blocks the first
  drag optimistically flipped resolves to `BreakDragMode.DROP` (the span is all `mineHere`), not a
  second claim, and the server's caller row lock plus the time-conflict check refuse a duplicate
  regardless.

- **Opt-out authorization.** `break_optouts` has own-row RLS for all four verbs
  (`20260531000002:36-59`), both clients write it directly via PostgREST rather than through a
  definer, and the opt-out is advisory: `claim_break_blocks` does not consult it, so an opted-out
  worker who changes their mind can still claim, exactly as BSpec section 4.4 specifies.

- **No em dashes or en dashes in break copy.** Scanned the break UI string literals on both mobile
  platforms and web, the migration-stored `COMMENT ON` and copy in `20260615000001` and
  `20260531000002`, and `break_periods.break_name` in the live database. Every hit was a code
  comment, which is exempt. The one gap is admin free text, filed as P3.
