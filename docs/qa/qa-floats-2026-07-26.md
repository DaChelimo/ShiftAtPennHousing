# Ship Check: Floats (slice 5)

Date: 2026-07-26
Journey: a desk will be empty, the system finds a worker at another house, moves them, tells them.
Covers: detection, selection, write, notify, acknowledge, decline, no-ack void, force trigger,
no-takeback, source-seat reopen.

Probes were run against the local stack at `postgresql://postgres:postgres@127.0.0.1:54322/postgres`
and `http://127.0.0.1:54321`. Two probes mutated real rows; both were snapshotted before, reverted by
exact primary key after, and the revert verified by diffing the seat rows against the pre-probe CSV
and re-checking the `float_assignments` / `notifications` / `block_step_status` row counts. All other
probes ran inside a rolled-back transaction.

### [P0] Any anonymous caller can float a worker out of their house, and can decline another worker's float

**Journey**: none. This is reachable by anyone who can read the app's public anon key, which every
copy of the mobile and web client ships.

**Trigger**: with only the project's anon key and no bearer token at all:

```
POST /rest/v1/rpc/force_trigger_float
  apikey: <anon key>
  {"p_initiator_user_id":"<any uuid>","p_worker_id":"<any worker>",
   "p_source_house_id":"harnwell","p_source_assignment_ids":["<their seat>"],
   "p_destination_assignment_ids":["<any vacant seat>"],
   "p_destination_house_id":"gutmann","p_now":"...","p_retention_days":14}
```

**Observed**: `HTTP 200 {"assigned": true, "float_id": "712d9aa8-..."}`. I ran exactly this, as
`anon`, and it wrote the full float: `float_assignments` row `initiated_by=force_triggered`; the
Harnwell worker Aaron's seat flipped `scheduled` to `pending_float_out`; the Gutmann seat flipped
`vacant` to `pending_float_in` with `source_house_id=harnwell`; a reopened vacant seat inserted at
Harnwell; 5 notification rows; and `broadcast` + `float_lookup` retired as
`completed_via_force_trigger` on the Gutmann block. All of it reverted afterwards.

Identity was established inside the same command: the credential's `role` claim is `anon`, and the
negative control in the same run, `POST /rest/v1/rpc/lock_block_coverage` with the identical
credential, returned `HTTP 401 {"code":"42501","message":"permission denied for function
lock_block_coverage"}`.

Live catalog, whole float path:

| function                          | anon | authenticated | definer |
| --------------------------------- | ---- | ------------- | ------- |
| `force_trigger_float`             | true | true          | true    |
| `process_float_lookup_assignment` | true | true          | true    |
| `process_no_ack_float`            | true | true          | true    |
| `process_hmod_notify_allied_step` | true | true          | true    |
| `process_broadcast_step`          | true | true          | true    |
| `acknowledge_float`               | true | true          | true    |
| `decline_float`                   | true | true          | true    |
| `snapshot_float_ack_reminders`    | true | true          | true    |
| `reopen_float_source_seats`       | true | true          | true    |
| `reconcile_float_source_release`  | true | true          | true    |
| `set_allied_resolved`             | true | true          | true    |

Cause is the shape `supabase/AGENTS.md` already names: every one of these migrations issues
`REVOKE ALL ON FUNCTION ... FROM PUBLIC` and never names `anon, authenticated`. See
`supabase/migrations/20260623000002_float_source_seat_reopen.sql:248` and
`supabase/migrations/20260601000002_phase_12_force_trigger_ack_reminders.sql:101`. The two functions
added by `20260726000011_float_coverage_concurrency.sql` DO name them (lines 57 and 117) and are
correctly `anon=false`, which is why they make a clean control.

The owner guard on the two worker-facing RPCs is also defeated by exactly this caller.
`decline_float` opens with `IF auth.uid() IS NOT NULL AND auth.uid() <> p_user_id THEN RAISE`; under
`anon`, `auth.uid()` is NULL, so the guard never fires. Proven with a control in one run:

- as `anon` with a mismatched `p_user_id`: `HTTP 200 {"reason":"not_pending","declined":false}`,
  meaning the guard did not fire and execution fell through to the row lookup;
- as a real signed-in worker (sub printed from GoTrue `/auth/v1/user` in the same command) with the
  same mismatched `p_user_id`: `HTTP 403 {"code":"42501","message":"cannot decline a float for
another user"}`.

So an anonymous caller who supplies the correct `p_user_id` can decline any worker's pending float:
voiding it, writing a `declined` `float_exclusion` against that worker, and reopening the
destination. `acknowledge_float` carries the identical guard and the identical hole.

**Expected**: these are service-role-only RPCs called by Edge Functions. `supabase/AGENTS.md`
("Rules"): a function meant to be service-role-only needs `REVOKE EXECUTE ON FUNCTION <fn> FROM anon,
authenticated;` naming those roles explicitly. AGENTS invariant #3 (no-takeback) also means a
stranger must not be able to void a pending float.

**Blast radius**: every house, every float, every worker. No authentication required. A single script
can empty a desk, burn float exclusions against workers, and retire escalation steps so the chain
never re-fires.

**Fix sketch**: one migration adding `REVOKE EXECUTE ON FUNCTION <fn>(<sig>) FROM anon,
authenticated;` for each of the eleven functions above, plus a pgTAP assertion per function that
names `anon` and `authenticated` explicitly (not `has_function_privilege('public', ...)`). Separately,
change the owner guard in `acknowledge_float` / `decline_float` from
`auth.uid() IS NOT NULL AND auth.uid() <> p_user_id` to a form that also refuses when
`auth.uid()` is NULL and the caller is not `service_role`.

**Acceptance check**: re-run the two probes above. `force_trigger_float` as `anon` must return
`42501 permission denied`, and `decline_float` as `anon` with a mismatched `p_user_id` must return
`42501`, not `not_pending`. `lock_block_coverage` stays the negative control.

**Confidence**: verified in code and at runtime (write performed and reverted).

This is a different set of functions from the four already ticketed (`claim_open_shift`,
`fire_worker`, `hire_worker`, `user_has_house_admin_role`), so it is filed rather than folded in.

### [P0] A no-acknowledged float can never be voided once someone picks up the floater's reopened home seat, and one such float freezes the no-ack pass for the whole system

**Journey**: the orchestrator floats Casey out of Rodin to cover Gutmann. Rodin's desk drops to one
worker, so Casey's home seat reopens in the open-shifts feed (this is the designed behavior of
migration `20260623000002`). Dana picks it up. Casey never acknowledges.

**Trigger**:

1. `process_float_lookup_assignment` assigns the float. `reopen_float_source_seats` inserts a vacant
   `temporary_drop` seat on the Rodin block.
2. Dana calls `claim_open_shift` on that seat. Rodin now has 2 occupied seats, required 2.
3. At T-15m the tick calls `process_no_ack_float`.

**Observed**: the RPC raises and the whole transaction rolls back. Exact output from my probe:

```
ERROR:  block_over_capacity: block 1111... already has 2 occupied seat(s); house headcount is 2
CONTEXT:  PL/pgSQL function enforce_block_occupied_headcount() line 54 at RAISE
SQL statement "UPDATE shift_block_assignments
    SET user_id = v_float.user_id, status = 'scheduled', ...
    WHERE assignment_id = ANY(v_float.source_assignment_ids)"
PL/pgSQL function process_no_ack_float(uuid,timestamp with time zone,integer) line 107
```

The offending statement is the automated-path `ELSE` branch at
`supabase/migrations/20260713000001_offhours_allied_ladder.sql:719-723`, which restores the floater to
their source seats unconditionally. `20260713000001` re-created `process_no_ack_float` and reverted
step 5 to the pre-`20260623000002` inline form: the `force_triggered` branch got the
claimed-seat-aware logic inlined, and the automated branch got the unconditional restore that
`20260623000002` had deliberately replaced with `reconcile_float_source_release`. Confirmed against
the live catalog: `process_no_ack_float`'s body contains zero references to
`reconcile_float_source_release`.

Control, on byte-identical state: `decline_float` (which still calls
`reconcile_float_source_release`, see the live body) returns `{"declined": true}`, correctly
displaces the floater to `vacant / displaced_decliner`, and lets Dana keep the seat.

Downstream consequences, all from the rollback:

- The float stays `pending`, so the Gutmann seat stays `pending_float_in`. That status is in the
  escalation present-set, so `orchestrator_vacant_seats` reports the desk as covered and the chain
  never fires. Nobody pages for Allied. The desk is empty at 18:00 with no alert.
- Casey is never restored to Rodin and never lands at Gutmann, so they hold no seat at all.
- `processVacantBlocks`'s sibling `processNoAckFloats` re-throws on the RPC error at
  `supabase/functions/orchestrator-tick/index.ts:731`, which aborts the entire no-ack pass. One
  poisoned float therefore stops every other float in the system from ever being voided, on every
  subsequent tick, until a human intervenes.

**Expected**: the no-ack void behaves exactly like a decline on the source side. `20260623000002`'s
own header states the rule: "seat was claimed / Allied took it, the claimer keeps it (first-come-
first-served), the floater is displaced (BSpec 6.6 #7)", and both behaviors were "extracted into
shared helpers so the automated and force-trigger paths can never diverge again."

**Blast radius**: every automated float whose reopened source seat gets picked up, which is the
outcome the reopen feature exists to produce. Once one occurs, all no-ack voids everywhere stop.

**Fix sketch**: in `process_no_ack_float`, replace the whole of step 5 (the
`IF v_float.initiated_by = 'force_triggered' ... ELSE ... END IF` block,
`supabase/migrations/20260713000001_offhours_allied_ladder.sql:690-724`) with a single
`PERFORM reconcile_float_source_release(p_float_id);`, matching `decline_float`. Separately, make
`processNoAckFloats` in `supabase/functions/orchestrator-tick/index.ts` collect per-float errors into
`summary.errors` instead of throwing, so one bad float cannot stop the pass.

The same unconditional-restore shape exists at
`supabase/migrations/20260719000001_house_transfers.sql:223-226` and will fail the same way. Fix it
there too or file it against slice 10.

**Acceptance check**: pgTAP. Assign an automated float, claim the reopened source seat, run
`process_no_ack_float`, assert `{"processed": true}`, assert the float is `voided`, assert the source
seats are `vacant / displaced_decliner`, and assert the claimer still holds their seat. Revert the
fix and confirm the test goes red with `block_over_capacity`.

**Confidence**: verified at runtime (rolled-back transaction, full output above).

### [P0] force-trigger never checks that the requested blocks belong to the house you claim, so a Student Manager can float a worker into a house they have no authority over, and the worker is told the wrong desk

**Journey**: a manager taps "Get coverage now" on an open seat. The request carries a
`destination_house_id` and a set of block or seat ids. Nothing on the server ties the two together.

**Trigger**: as `sam-du-bois@upenn.edu`, whose only role row is `sm @ du-bois`:

```
POST /functions/v1/force-trigger/force-trigger
  {"destination_house_id":"du-bois",
   "block_ids":["8683aed5-..."]}     <- this block belongs to GUTMANN
```

**Observed**: `HTTP 200 {"ok":true,"floatAssignmentIds":["eb8dea2f-..."]}`. The resulting rows:

```
FLOAT  eb8dea2f-...  user=Aaron  home=harnwell  initiated_by=force_triggered  forced_by=<the du-bois SM>
SEAT   house=gutmann  status=pending_float_in   user=Aaron  src_house=harnwell
SEAT   house=harnwell status=pending_float_out  user=Aaron
SEAT   house=harnwell status=vacant                        (reopened)
NOTIF  personal_shift  payload={"kind":"float_assigned", ..., "destination_house_id": "du-bois"}
STEP   gutmann block  broadcast      completed_via_force_trigger
STEP   gutmann block  float_lookup   completed_via_force_trigger
```

An SM of Du Bois pulled a Harnwell worker off the Harnwell desk and put him on the Gutmann desk. The
notification he receives names `du-bois`.

Negative control in the same run: identical `block_ids`, truthful `destination_house_id: "gutmann"`,
same token: `HTTP 403 {"error":"force_trigger_rejected","reason":"unauthorized_initiator"}`. And with
a within-2h Gutmann block plus the `du-bois` lie: `HTTP 409 reason: within_two_hours`, which ranks
BELOW `unauthorized_initiator` in the validator's fixed precedence, so authorization had already
passed. Identity printed from GoTrue `/auth/v1/user` in the same command.

Where it goes wrong:

- `supabase/functions/force-trigger/index.ts:640` loads the initiator's roles with
  `loadRolesAtHouse(supabase, initiator, destinationHouseId)`, that is, scoped to the caller-supplied
  string.
- `packages/core/src/force-trigger/validation.ts:39` destructures
  `{ initiator, blocks, now, floatEnabled }` and never reads `destinationHouseId`. None of the six
  checks compares a block's house to it.
- `loadBlockSnapshots` (`supabase/functions/force-trigger/index.ts:236-296`) reads each block's
  `house_id` into `gapRows` and never compares it either.
- `force_trigger_float` (`supabase/migrations/20260726000011_float_coverage_concurrency.sql:313`)
  takes `p_destination_house_id` as a parameter and uses it only for the notification body and the
  ack-cadence lookup. It never derives the destination house from the blocks it is writing.

Three further consequences of the same missing check:

1. `snapshot_float_ack_reminders` is called with the lied house
   (`20260726000011:529-531`), so the 6h/2h cadence is read from `ack_cadence_config` for the wrong
   house.
2. The float lookup runs against `float_routing` for the lied destination, so the source pool and its
   precedence order are the wrong house's.
3. The Harnwell-is-never-a-destination guard is defeated. It lives only in
   `packages/core/src/float-lookup/index.ts:202` as
   `if (gap.destinationHouseId === HARNWELL_HOUSE_ID)` and in the `float_routing` legality trigger
   (`enforce_float_routing_legality`, live body confirmed). Neither sees the blocks. Passing Harnwell
   `block_ids` with a non-Harnwell `destination_house_id` short-circuits neither, and no write-point
   check exists: the only Harnwell guard on `shift_block_assignments` is
   `enforce_harnwell_assignment_training` (`supabase/migrations/20260527000005_schedule_builder.sql:378`),
   which only checks the floater's `home_house_id`. A Harnwell-home floater therefore lands on a
   Harnwell block.

**Expected**: `supabase/AGENTS.md` "Authorization predicates, do not collapse them", invariant 2:
"SM never gains cross-house power." AGENTS hard invariant #2b: Harnwell is never a float destination,
and that guard is "never trusted from config" (nor, by the same reasoning, from a request body).
AGENTS hard invariant #1 requires enforcement "at every assignment write point, not only in config
tables"; the same standard applies to the destination-house guard.

**Blast radius**: any signed-in SM, plus (per the P0 above) any anonymous caller who skips the Edge
Function entirely. The ordinary mobile and web clients always send a matching pair, so this does not
fire by accident; it fires when someone sends a request by hand.

**Fix sketch**: in `supabase/functions/force-trigger/index.ts`, derive `destinationHouseId` from the
resolved blocks and reject when the blocks span more than one house or disagree with the body value,
before `loadRolesAtHouse` is called with it. Add `destinationHouseId` plus a per-block `houseId` to
`ForceTriggerBlockSnapshot` and make `validateForceTrigger` reject `house_mismatch` ahead of the
authorization check. In `force_trigger_float` and `process_float_lookup_assignment`, stop trusting
`p_destination_house_id`: resolve the house from `shift_blocks` via the destination assignment ids,
raise on a mismatch, and raise when that resolved house is `harnwell`.

**Acceptance check**: replay the probe. `destination_house_id: "du-bois"` with a Gutmann block must
return 403 or a `house_mismatch` rejection with no rows written. pgTAP: `force_trigger_float` with
`p_destination_house_id` disagreeing with the destination blocks' house must raise, and with Harnwell
destination blocks must raise regardless of the floater's home house.

**Confidence**: verified in code and at runtime (write performed and reverted; negative control run).

### [P0] Between T-15m and T-10m the app tells a worker "Confirmed, you're covering X" for a float the server already voided and sent to Allied

**Journey**: a worker gets the float push, opens the app a bit late, sees "Accept by 17:50, 4m left"
with a live Accept button, taps Accept, and gets a confirmation.

**Trigger**:

1. Float destination starts at 18:00. Acknowledgment deadline is 17:50 (T-10m).
2. At 17:45 (T-15m) the orchestrator's no-ack pass voids the float, writes a `no_acknowledgment`
   `float_exclusion` against the worker, reopens the destination, and pages for Allied.
   `loadRuntimeConfig` computes `noAckLookaheadMinutes = ack_deadline(10) + no_ack_trigger(5) = 15`
   (`supabase/functions/orchestrator-tick/index.ts:86-95`), `pending_floats_due_for_no_ack` selects on
   `min(block_start_at) <= now + 15 minutes`, and `process_no_ack_float` voids. I confirmed at
   runtime that calling it at `block_start - 14 minutes` proceeds past the `outside_lookahead` guard
   and voids.
3. At 17:47 the worker taps Accept. `canRespondToFloat` is
   `now < ackDeadline(floatStart)` (`apps/mobile/shared/src/commonMain/kotlin/com/pennhousing/shift/shared/ack/Ack.kt:43-46`),
   which is still true, so both clients render live Accept/Decline and the countdown
   "Accept by 17:50 · 3m left" (`.../ack/FloatCarousel.kt`, `acceptByLabel`).

**Observed**: `acknowledge-float` returns `HTTP 200 {"reason":"not_pending","acknowledged":false}` and
writes nothing. I verified this exact response against the running Edge Function, as a signed-in
worker whose sub was printed in the same command, with the float row confirmed unchanged afterwards.
`supabase/functions/acknowledge-float/index.ts:112` returns the RPC's negative result with a 200 and
no status branch.

Both clients treat that as success:

- `EdgeResult.ok = response.status.isSuccess()`
  (`apps/mobile/shared/src/commonMain/kotlin/com/pennhousing/shift/shared/network/EdgeFunctionClient.kt:69`),
  so `ok` is true.
- Android: `launchWrite(WriteOp.ACK_FLOAT)` only toasts and reverts when `!result.ok`
  (`apps/mobile/androidApp/src/main/java/com/pennhousing/shift/MainActivity.kt:536-541`, called at
  line 772). No revert, no error.
- iOS: `liveWrite(.ackFloat, revert: false) { try? await repo.acknowledgeFloat(...) }`
  (`apps/mobile/iosApp/iosApp/ContentView.swift:1342-1350`) discards the result entirely.

The ack hero was already flipped optimistically, so it shows eyebrow "Acknowledged", headline
"You're covering <house>", status line "Confirmed · read-only"
(`apps/mobile/shared/src/commonMain/kotlin/com/pennhousing/shift/shared/ack/FloatAckPresentation.kt`).
The worker drives to a desk that Allied was paged to cover.

**Expected**: the client must not offer Accept past the point the server will honour it, and a
response of `acknowledged: false` must not be rendered as success. BSpec 7.3 sets the void at 5
minutes before the deadline, and BSpec 7.1 sets the deadline at T-10m, so the two are 5 minutes
apart by design; the client's respond window must therefore end at the void point, not the deadline,
or the spec must move the void to the deadline. Either way the mismatch between what the app promises
and what the server does is the defect.

**Blast radius**: every float the worker responds to in the last 5 minutes. This is precisely the
population most likely to be late, which is the population the no-ack path exists for.

**Fix sketch**: two changes, both needed.

1. Make the clients honour the server's answer: have `acknowledgeFloat` / `declineFloat` in
   `apps/mobile/shared/.../data/WorkerShiftsRepository.kt` parse `acknowledged` / `declined` from the
   body and return failure when it is false, so Android's `launchWrite` reverts and toasts and iOS's
   `onFailure: revertAck` fires. Alternatively make
   `supabase/functions/acknowledge-float/index.ts:112` and its decline twin return 409 for
   `not_pending`.
2. Close the window in the shared logic: `canRespondToFloat` in `.../ack/Ack.kt` should subtract the
   no-ack trigger offset as well, so the countdown and the buttons end at T-15m, and the copy should
   say what the worker actually has.

**Acceptance check**: kotlin.test on `canRespondToFloat`: at `floatStart - 12 minutes` it must be
false. Manual: with the sim clock at `floatStart - 12m`, tap Accept and confirm the app shows a
failure toast and returns to PENDING rather than "Confirmed · read-only".

**Confidence**: verified in code and at runtime for the HTTP behaviour; the client rendering is
verified in code.

### [P0] Dropping a float you already acknowledged leaves the system telling you that you are still covering it

**Journey**: a worker acknowledges a float, then something comes up, so they open My Shifts, tap the
float shift, and drop it.

**Trigger**: full probe output, run in a rolled-back transaction:

1. Automated float assigned, then `acknowledge_float`. Source seat `floated_out`, destination seat
   `floated_in`.
2. `worker_my_shifts` shows the destination seat as `kind = float_out`, house `Gutmann`. Mobile's
   `dropOptionsFor` returns `canDropOccurrence = true` unconditionally for every kind
   (`apps/mobile/shared/src/commonMain/kotlin/com/pennhousing/shift/shared/shifts/Shifts.kt:255-259`),
   so the Drop control is offered.
3. `drop_shift([destination seat], worker, now)` returns success.

**Observed**:

```
destination seat : vacant | temporary_drop | parent_float_id = NULL
float_assignments: status = acknowledged, acknowledged_at set
source seat      : still floated_out
```

`drop_shift` accepts `floated_in` / `pending_float_in` / `floated_out` / `pending_float_out` as
droppable statuses (`supabase/migrations/20260726000009_seat_write_compare_and_swap.sql:85-86`, and
the same list on the compare-and-swap `UPDATE` at line 148-149) and never touches
`float_assignments`.

The float row is still joined by `worker_recent_floats` through `destination_assignment_ids`, so it
still appears, with `status = 'acknowledged'`. `WorkerShiftsRepository.kt:1460` maps that to
`RecentFloatStatus.ACCEPTED`, which `buildRecentFloatRows` renders as detail "You're covering" and
chip "Accepted" (`.../ack/RecentFloatPresentation.kt`). The worker's own app tells them they are
covering a shift they dropped. Per BSpec 7.1 the destination house's SM sees the same acknowledgment
status on their dashboard, so the receiving house also believes a floater is coming.

The worker also ends up holding neither seat: the source stays `floated_out` and the destination is
vacated.

**Expected**: a float has exactly three terminal states in the spec, acknowledged, declined, voided.
Vacating its destination seat must move the `float_assignments` row out of `acknowledged`, and the
worker must not be shown a shift they no longer hold. Anything else is "told something false about
their own schedule."

**Blast radius**: every acknowledged float, on both platforms, with no race and no unusual timing
required. It is a two-tap path from the main screen.

**Fix sketch**: decide the product rule first, then implement one of:
(a) refuse it, by removing `floated_in` / `pending_float_in` / `floated_out` / `pending_float_out`
from `drop_shift`'s accepted status list and having `dropOptionsFor` return
`canDropOccurrence = false` for `AssignmentKind.FLOAT_OUT`, pointing the worker at decline instead; or
(b) allow it and reconcile, by adding a trigger or an explicit branch in `drop_shift` that, when a
dropped seat carries a `parent_float_id` or appears in a float's `destination_assignment_ids`, moves
the float to `voided` and runs `reconcile_float_source_release`.
Either way `worker_recent_floats` must stop reporting `acknowledged` for a float whose destination
seat the worker no longer holds.

**Acceptance check**: pgTAP. Acknowledge a float, drop the destination seat, then assert
`float_assignments.status <> 'acknowledged'` and that `worker_recent_floats` for that worker does not
report `acknowledged` for it. Mobile: a `MyShiftPresentation` / `dropOptionsFor` test asserting the
chosen rule for `FLOAT_OUT`.

**Confidence**: verified at runtime for the database state; the mobile rendering is verified in code.

### [P0] A house transfer voids an acknowledged float and nobody tells the worker

**Journey**: a manager transfers a worker to another house, effective next Monday. On Monday the
hourly cron applies it. The worker had already acknowledged a float for Monday evening.

**Trigger**:

1. `transfer_worker(..., p_effective_date => <a future date>)` records the membership.
2. The `apply-house-transfers` pg_cron job (scheduled at
   `supabase/migrations/20260719000001_house_transfers.sql:528`) calls `apply_due_house_transfers()`,
   which calls `apply_house_transfer` at line 506.
3. `apply_house_transfer` loops over the worker's floats
   `WHERE status IN ('pending', 'acknowledged') FOR UPDATE`
   (`supabase/migrations/20260719000001_house_transfers.sql:200-205`), sets each to `voided`, vacates
   the destination seats, restores the source seats, and deletes the reopened gap rows (lines
   206-232).

**Observed**: the whole migration file contains zero `INSERT INTO notifications` statements (verified
by count). The worker's acknowledged float vanishes with no push, no in-app message, and no entry
that explains it. They see it only if they happen to reopen the app and notice the shift is gone. The
same run then permanently drops their old-house recurring seats (step (b), lines 237 onward), so
their week changes substantially in one silent operation.

The contrast is in the same codebase: `apply_compiled_season`'s downsize path notifies every
cancelled worker, with `shift_cancelled_config` and `float_cancelled_config` payloads
(`supabase/migrations/20260709000003_season_downsize_cancel_excess.sql:191, 250, 327`). The float
path in `apply_house_transfer` is modelled on `fire_worker` and inherited its silence.

The unconditional source restore at lines 223-226 also carries the same
`enforce_block_occupied_headcount` failure mode proven in the no-ack ticket above: if the floater's
reopened home seat was picked up by someone else, this `UPDATE` raises `block_over_capacity` and the
whole transfer aborts. Since it runs from cron, it will retry hourly and fail hourly.

**Expected**: BSpec 10.1 makes personal notifications mandatory. A worker whose acknowledged
commitment is cancelled must be told, exactly as the season-downsize path tells them. AGENTS
invariant #3 permits a manual admin action to revoke a float; it does not permit doing so silently.

**Blast radius**: every worker with a live float on their transfer day. Low frequency, total impact
on the individual: they lose the float hours and the app never says why.

**Fix sketch**: inside the float loop in `apply_house_transfer`
(`supabase/migrations/20260719000001_house_transfers.sql:200-235`), add a `personal_shift`
notification per voided float, matching the `float_cancelled_config` shape used by
`20260709000003`, with a reason distinguishing a transfer from a config change. Replace the

### [P2] The orchestrator's overlap guard never holds the lock it takes

**Journey**: none directly. This is a cost guard whose comment claims a property it does not have.

**Trigger**: two orchestrator ticks starting within the same minute.

**Observed**: `try_orchestrator_tick_lock` is
`SELECT pg_try_advisory_xact_lock(hashtext('shift.orchestrator'), 1)`
(`supabase/migrations/20260726000007_bulk_apply_and_tick_serialization.sql:60-67`). The tick calls it
as a standalone PostgREST RPC (`supabase/functions/orchestrator-tick/index.ts:911`), and PostgREST
runs each RPC in its own transaction, so the transaction-scoped lock is released the instant that
call commits, before the tick does any of its work.

Measured: calling the RPC over the same PostgREST path returned `true`; immediately afterwards
`SELECT count(*) FROM pg_locks WHERE locktype='advisory' AND classid = hashtext('shift.orchestrator')::int`
returned `0`; a second caller a moment later also got `true`. The guard can never return `false`.

The sibling use in the same migration is correct: `apply_compiled_season` takes the lock inside the
same transaction as the work it guards (line 114), so that one does hold.

**Expected**: the comment at `supabase/functions/orchestrator-tick/index.ts:896-918` and the
`COMMENT ON FUNCTION` at `20260726000007:72-76` both describe a working overlap guard. Filed at P2
rather than higher because the migration's own header is explicit that correctness never depended on
it: `block_step_status` upserts and the `FOR UPDATE` RPCs prevent double-firing. The cost is real but
no user loses anything.

**Fix sketch**: either move the guard into a `pg_advisory_lock`-style session lock held across the
tick, or use a session-scoped lock keyed to a dedicated connection, or replace it with an
`orchestrator_health.tick_in_flight` marker written and cleared by the Edge Function. If none of
those is worth it, delete the RPC and the call and correct both comments, so the next person does not
believe an overlap is impossible.

**Acceptance check**: the same three-step measurement above. After the fix, the second caller during
an in-flight tick must return `false`, and `pg_locks` must show the advisory lock held for the tick's
duration.

**Confidence**: verified at runtime.

## Verified clean

Each of these is a surface I walked on this slice and believe is genuinely sound, with the guard that
makes it so.

- **The coverage floor is still one worker, not required headcount.**
  `orchestrator_vacant_seats` (live body) computes `desk_covered` as
  `EXISTS (... status IN ('scheduled','claimed','floated_in','pending_float_in','allied'))` with no
  comparison to `required_headcount`, `processVacantBlocks` skips covered rows
  (`supabase/functions/orchestrator-tick/index.ts:579`), and `loadVacantGap` independently excludes
  covered blocks from the contiguous run via `loadCoveredBlockIds`
  (`supabase/functions/orchestrator-tick/floatLookup.ts:187-190`). Both call sites intact.

- **The two present-sets are not collapsed.** Three distinct predicates exist and each is used where
  it should be: `block_has_escalation_coverage` includes `allied`
  (`20260726000011:41-54`) and is what `lock_block_coverage` consults;
  `block_has_present_worker` excludes it and is what `claim_open_shift` consults for the T-2h
  exemption (live body, `IF v_target.block_start_at <= p_as_of + interval '2 hours' AND NOT
block_has_present_worker(...)`); the source-floor guard in `process_float_lookup_assignment` uses
  the real-worker set deliberately (`20260726000011:249`).

- **`lock_block_coverage` is a genuine check-and-lock and both callers abort on `false`.** It locks
  the block's seats `ORDER BY assignment_id FOR UPDATE`, re-evaluates coverage under that lock, and
  returns `false` without stamping (`20260726000011:91-112`). `floatLookupStep` returns `'covered'`
  (`floatLookup.ts:474-477`), `hmodNotifyAlliedStep` returns `'covered'`
  (`index.ts:412-415`), and `processVacantBlocks` breaks the chain and releases the claimed
  `float_lookup` step on `'covered'` (`index.ts:648-653`), which is what keeps a later drop able to
  re-escalate.

- **The tentative counter is still global per source.** `findFloaters` increments
  `tentativeFloatingOut` unconditionally after every selection, with no span-length or block-position
  condition (`packages/core/src/float-lookup/index.ts:268`). The removed hybrid heuristic has not
  been reintroduced. `sourceHasFloor` and `workerBlocksRespectSourceFloor` both read the counter
  (`packages/core/src/float-lookup/eligibility.ts:43-77`).

- **The three-tier partial-coverage fallback is intact and the floor is 1.** Full coverage, then
  leading span, then largest consecutive with the `allowTrailingPartial` non-trailing filter on the
  first iteration at each source (`packages/core/src/float-lookup/index.ts:141-195`, `234`).

- **The hours cap is not checked on the float path.** `FloatLookupInput` has no cap field
  (`packages/core/src/float-lookup/types.ts`), `getEligibleWorkersForSource` performs no cap check,
  and neither `process_float_lookup_assignment` nor `force_trigger_float` reads
  `effective_weekly_cap`. Invariant #4 holds in the correct direction.

- **The Allied 4-hour cap is enforced twice.** `loadVacantGap` bounds the query window at
  `block_start + MAX_ALLIED_COVERAGE_BLOCKS * blockMinutes` and additionally truncates the assembled
  run at 8 entries (`supabase/functions/orchestrator-tick/floatLookup.ts:146-208`), so the cap holds
  regardless of `blockMinutes`. The no-ack void draws its window from the float's destination blocks,
  which come from that capped gap, so it is transitively bounded.

- **Both assignment paths snapshot the ack-reminder cadence, through the one shared helper.**
  `PERFORM snapshot_float_ack_reminders(...)` appears in `process_float_lookup_assignment`
  (`20260726000011:301-303`) and in `force_trigger_float` (`20260726000011:529-531`). The known past
  audit gap has not reopened.

- **Null offset does not mean suppressed.** `snapshot_float_ack_reminders` gates presence on
  `COALESCE(v_cfg.reminder_6h_enabled, true)` and resolves the instant with
  `v_ack_deadline + COALESCE(v_cfg.reminder_6h_offset, interval '-6 hours')`
  (`20260601000002:79-84`). An enabled reminder with a NULL offset fires at the default.

- **The reminder offsets are DST-safe.** Every reminder instant is computed as a `timestamptz` plus an
  hour or minute interval, which in Postgres is exact duration arithmetic, never wall-clock. The gap
  end is likewise `max(block_start_at) + interval '30 minutes'`. No `AT TIME ZONE` round-trip and no
  day-unit arithmetic appears anywhere in the reminder or deadline computation.

- **An acknowledgment racing the no-ack void cannot both win.** Both `acknowledge_float` and
  `process_no_ack_float` take the float row with
  `SELECT * ... WHERE float_id = ... AND status = 'pending' ... FOR UPDATE`, so the loser's predicate
  is re-checked under the lock and it falls into its `IF NOT FOUND` branch. Verified in both live
  bodies.

- **Two floats can no longer be written into the same desk, and a source desk can no longer be
  emptied by two concurrent floats.** Both writers take every seat on every touched block in one
  ascending-`assignment_id` statement before any check, then run the competing-`pending_float_in`
  guard and the source-floor guard under that lock
  (`20260726000011:162-255` and `342-441`). The prelude is identical in both, so the automated and
  manual paths cannot defeat each other.

- **`float_routing` cannot be configured to make Harnwell a destination or a house float to itself.**
  `enforce_float_routing_legality` raises on both (live body confirmed), and the live table has zero
  rows with `destination_house_id = 'harnwell'`. The algorithm short-circuits independently at
  `packages/core/src/float-lookup/index.ts:202`. The gap is only at the assignment write point, filed
  in the force-trigger P0 above.

- **The floater's in-app view of which house and which hours is derived from the blocks, not from the
  caller-supplied house string.** `worker_pending_floats` and `worker_recent_floats` both compute
  `destination_house_id` and `destination_house_name` by joining
  `destination_assignment_ids` to `shift_blocks` and `houses`, and compute
  `float_start` / `float_end` as `min(block_start_at)` and `max(block_start_at) + 30 minutes` (live
  view definitions). So the float carousel and the ack hero name the right desk and the right window
  even in the force-trigger house-lie case. Only the notification payload carries the lied value.

- **The blank-body guard on push.** `pushDisplayFromData`
  (`apps/mobile/shared/.../ack/FloatDeepLink.kt`) always resolves a title and body, falling back to
