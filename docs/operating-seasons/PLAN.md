## 1. Goal

Add a top-level **admin** account (operated by the project owner in v1, grantable to
others later) that can _configure the operating system itself_ — which houses are
active on which dates, each house's headcount over time, whether floating is on, and
float routing — so that summer's dynamics are first-class:

Motivating real examples (Summer 2026):

- Lauder was closed the first half of summer, open the second half.
- Gregory opened at the start of June; Lauder opened mid June (houses open when they
  start receiving residents).
- Rodin was single-staffed until the 2nd week of June, double-staffed since.
- Floating was OFF in the first half of summer, ON in the second half.

Everyone below the admin (BM, HM, RSM, SM, SW) consumes the admin-modified dataset
through the exact same runtime paths they use today.

## 2. Pinned stakeholder decisions (2026-07-02)

These were confirmed explicitly with the stakeholder; do not re-litigate:

1. **Summer floating is UNIVERSAL (revised 2026-07-02, superseding the original
   admin-authored routing matrix).** When floating is on in a summer phase, any open,
   multi-staffed house may float a worker to any OTHER open house. There is no per-season
   routing matrix to author (`season_float_routes` and the routing UI panel were removed);
   the compiler auto-generates all-pairs routing via `generateRoutes`, precedence by
   descending source headcount. Harnwell MAY source. Non-negotiable guards remain in code:
   - Nobody ever floats INTO Harnwell (destination = harnwell short-circuits to Allied).
   - No worker whose home_house != Harnwell may staff the Harnwell desk by ANY
     mechanism (hard invariant #1, unchanged, enforced at every assignment write point).
   - A house may only source floats while its phase headcount is >= 2.
   - A source desk never drops below 1 present worker on any lent block.
   - This AMENDS hard invariant #2 (was class-based "only Quad/Harnwell source") to
     config-based-with-guards. School-year seed routing data is unchanged, so
     school-year behavior stays byte-identical.
2. **Admin is a full superuser.** Beyond the config editor: cross-house schedule write
   (everything `user_is_schedule_admin` grants), people admin (hire/fire, role grants)
   in ALL houses, weekly caps, force-trigger. This deliberately widens
   `user_has_house_admin_role` for the `admin` role only (stakeholder decision
   2026-07-02; supersedes the "do not widen" note in AGENTS.md for this one role).
3. **Mid-season config changes auto-apply with preview + grandfathering.** Changes are
   prospective from their effective date. Apply shows a preview (seats added,
   assignments voided, workers notified) then reconciles automatically. Occupied seats
   above a REDUCED headcount are grandfathered (kept + flagged), never auto-removed.
4. **Summer scheduling is SM-built**, like the school year (scheduling_mode
   `sm_built`). Seats created by mid-summer changes are filled via override/claims,
   not republish.

Baked-in defaults (stakeholder saw these and did not object):

- Harnwell invariants absolute in every season.
- Hours cap, cap enforcement (soft/hard), and desk operating hours are
  admin-configurable per season/phase.
- No-takeback holds for floats in flight when floating toggles off at a phase boundary
  (automated systems never revoke; season apply is a MANUAL override and MAY void, see §9).
- The HMOD rotor auto-extends into summer once summer dates become operating dates
  (rotor weeks already derive from scheduling_periods ∩ operating_calendar). Populating
  it is a go-live checklist item, not new code.
- Mobile stays worker-only; all filtering happens server-side in views/RPCs so mobile
  ships unchanged.

## 4. Design overview

**Authoring layer + compiler + reconciler.** We do NOT retrofit date-effectivity into
the four runtime tables, and we do NOT make the orchestrator/generator read new tables.
Instead:

1. The admin edits a high-level **season** model (new tables, §5): per-house open
   windows with headcounts, float windows, a routing matrix, season-level settings.
2. A **compiler** (pure TS in packages/core) derives _phases_: every date where ANY
   setting changes is a phase boundary. Each phase materializes into the EXISTING
   config tables — one compiled `operating_profiles` row, its `staffing_patterns` and
   `float_routing` rows, and `operating_calendar` rows for the phase's dates.
3. A **reconciler** (SQL RPC, single transaction) diffs the compiled target state
   against existing future blocks/seats/assignments and applies the §9 policy.

Why: every runtime consumer (orchestrator tick, block generator, publish, claim,
force-trigger `float_enabled` check, feeds) already keys off the four tables. Compiling
into them means ZERO changes to the escalation/generation/publish machinery and keeps
school-year behavior untouched by construction. The rejected alternative (date-ranged
runtime tables like `house_activation_windows`) would touch every consumer and multiply
the test surface.

This maps 1:1 to the stakeholder's mental model: "first half of summer" and "second
half of summer" are just phases.

```
admin UI (web)  →  season tables (authoring truth)
                        │  compile (pure TS, packages/core)
                        ▼
        compiled phases payload (jsonb)
                        │  apply_compiled_season RPC (dry_run | apply)
                        ▼
operating_profiles + staffing_patterns + float_routing + operating_calendar
                        │  reconcile (same RPC transaction)
                        ▼
shift_blocks / shift_block_assignments (generate, add seats, void, grandfather)
```

### 5.3 Migration C — season authoring tables

```sql
CREATE TABLE operating_seasons (
  season_id        uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  season_name      text NOT NULL,                      -- 'Summer 2026'
  slug             text NOT NULL UNIQUE,               -- 'summer2026', used in compiled profile names
  start_date       date NOT NULL,
  end_date         date NOT NULL CHECK (end_date >= start_date),
  scheduling_mode  scheduling_mode_enum NOT NULL DEFAULT 'sm_built',
  hours_cap        integer NOT NULL,
  cap_enforcement  cap_enforcement_enum NOT NULL,
  shift_start_bound time NOT NULL DEFAULT '08:00',
  shift_end_bound   time NOT NULL DEFAULT '00:00',     -- 00:00 means 24:00 (repo convention)
  last_applied_at  timestamptz,
  created_by       uuid REFERENCES users (user_id),
  created_at       timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE season_house_windows (
  window_id   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  season_id   uuid NOT NULL REFERENCES operating_seasons ON DELETE CASCADE,
  house_id    text NOT NULL REFERENCES houses (id),
  start_date  date NOT NULL,
  end_date    date NOT NULL CHECK (end_date >= start_date),
  headcount   integer NOT NULL CHECK (headcount >= 1),
  band_headcounts jsonb                                -- optional; same shape as staffing_patterns.block_headcounts; NULL = one full-day band at `headcount`
);
-- presence of a window = house OPEN for those dates; no window = closed
-- add an EXCLUDE or trigger preventing overlapping windows per (season, house)

CREATE TABLE season_float_windows (
  window_id  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  season_id  uuid NOT NULL REFERENCES operating_seasons ON DELETE CASCADE,
  start_date date NOT NULL,
  end_date   date NOT NULL CHECK (end_date >= start_date)
);
-- floating ON during windows, OFF elsewhere in the season; prevent overlaps per season

CREATE TABLE season_float_routes (
  season_id            uuid NOT NULL REFERENCES operating_seasons ON DELETE CASCADE,
  source_house_id      text NOT NULL REFERENCES houses (id),
  destination_house_id text NOT NULL REFERENCES houses (id),
  precedence_order     integer NOT NULL,
  PRIMARY KEY (season_id, source_house_id, destination_house_id),
  CHECK (destination_house_id <> 'harnwell'),
  CHECK (source_house_id <> destination_house_id)
);
-- season-wide matrix; the compiler prunes it per phase (see §7)

CREATE TABLE operating_config_audit (
  audit_id   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  season_id  uuid REFERENCES operating_seasons,
  action     text NOT NULL,          -- 'apply' | 'preview' (log applies at minimum)
  applied_by uuid REFERENCES users (user_id),
  applied_at timestamptz NOT NULL DEFAULT now(),
  payload    jsonb NOT NULL,         -- compiled phases payload
  impact     jsonb NOT NULL          -- the reconciliation summary returned to the UI
);
```

RLS: all five tables admin-only (`user_is_admin(auth.uid())`) for ALL verbs +
service-role bypass. Lower roles never read authoring tables; they consume compiled
tables through existing paths.

## 7. Compiler spec (packages/core/src/operating-seasons/)

Pure TS, zero Supabase imports, deterministic, injected `today` — mirror the
float-lookup purity pattern. Vitest-tested.

Input: season row + house windows + float windows + routes (plain objects).
Output: `CompiledSeason`:

```ts
type CompiledPhase = {
  profileName: string;            // `s_<slug>_<YYYYMMDD>` (phase start date) — stable per boundary
  startDate: string; endDate: string;          // NY dates, inclusive
  floatEnabled: boolean;
  escalationChain: ChainStep[];   // float on  → broadcast -3h, float_lookup -2h, hmod_notify_allied -2h on_float_failure
                                  // float off → broadcast -3h, hmod_notify_allied -2h   (winter_break shape)
  houses: Array<{ houseId: string; blockHeadcounts: BandJson[] }>;  // only OPEN houses
  floatRouting: Array<{ source: string; destination: string; precedence: number }>;
};
type CompiledSeason = { seasonId: string; phases: CompiledPhase[]; periodRow: {...} };
```

Rules:

- Phase boundaries = union of: season start/end, every house-window start and end+1,
  every float-window start and end+1. Merge adjacent phases whose full compiled content
  is identical.
- `staffing_patterns` rows are emitted for BOTH day_types with the same bands (v1
  simplification, matches current seed; schema already supports splitting later).
- Route pruning per phase: drop a route when (a) floating is off in the phase, (b) the
  source house is closed OR its phase headcount max is < 2, (c) the destination house
  is closed. (Harnwell-destination and self-routes are already impossible via CHECKs.)
- Profile field mapping: `scheduling_mode`, `default_hours_cap`,
  `default_cap_enforcement`, `shift_start_bound`, `shift_end_bound` from the season
  row; `claim_phase_*` = NULL (sm_built); bands must lie within
  [start_bound, end_bound) honoring the `'00:00'` = 24:00 convention (validate).
- Validation errors (compile fails, nothing applied):
  - overlapping windows per house / overlapping float windows;
  - windows outside the season range;
  - any season date already mapped in `operating_calendar` to a profile NOT owned by
    this season (never clobber school year; re-applying over your own compiled rows is
    fine);
  - season overlapping another season's range;
  - phase boundary in the past or today (all effective dates must be >= tomorrow NY;
    editing the current day mid-flight is forbidden — see §9 timing rule);
    EXCEPTION: re-applying a season whose earlier phases are already live is allowed as
    long as all _changed_ content is >= tomorrow NY (diff-aware check).
- Also emits one `scheduling_periods` row spec for the season (period_name =
  season_name, range = season range, profile_name = first phase's profile) so the
  builder/preferences/rotor machinery anchors on it. **Verify** every reader of
  `scheduling_periods.profile_name` tolerates a compiled profile (audit task §16.1).

## 8. Apply path

Web server action (admin-gated) → loads authoring rows → runs compiler → calls
`apply_compiled_season(p_calling_user_id uuid, p_season_id uuid, p_payload jsonb,
p_dry_run boolean)` (SECURITY DEFINER; re-checks `user_is_admin`; re-validates the §5.4
guards on payload contents at the DB layer).

Single transaction, in order:

1. Upsert compiled `operating_profiles`; delete+reinsert their `staffing_patterns` and
   `float_routing`; upsert the season's `scheduling_periods` row FIRST (FK on
   profile_name — order matters); rewrite `operating_calendar` rows for the season's
   date range. Orphaned compiled profiles from prior applies are left in place (inert
   once unreferenced by the calendar) — do NOT delete rows other tables may FK.
2. Reconcile blocks/seats/assignments per §9 (future blocks only).
3. Insert `operating_config_audit` row; return the impact summary jsonb.

`p_dry_run = true` computes the same impact via SELECTs and writes nothing (this is the
preview). Preview and apply share the same CTE logic so they cannot drift.

progress or past are immutable history. Additionally the compiler forbids changing
today's config (§7), so the orchestrator's ~3h lookahead never sees config mutate
mid-escalation. Preview flags any affected block starting within 24h.

## 18. Summer preference-based scheduling (extension, planned 2026-07-03)

Summer is `sm_built` (decision #4), so like the regular school year it should be built
from worker preferences: before summer starts, workers key in the shifts they want, and
the SM builds from those. The preference plumbing is already period-generic (it keys off
`period_id`, not profile), so it works for a summer period today. Two gaps: the deadline
is not admin-authored on the season, and the spec scopes preferences to the school year
only. This extension closes both, plus stands up a test world.

Decisions (stakeholder, 2026-07-03):

- **D1 admin surface** = the season editor. The preference deadline is authored on the
  season in `/admin/operations`, one streamlined place for all houses (periods are global,
  so one deadline covers every house).
- **D2 window model** = close-deadline only (open immediately, closes at the deadline),
  matching the school year. No explicit open date.
- **D3 who may set** = add the top-level `admin` role to the existing SM/HM/BM setters of
  `set_preference_deadline` (via `user_is_admin()`); do not remove SM/HM/BM.
- **D4 test seed** = an OPEN window plus PARTIAL pre-seeded preferences (some workers
  filled, some blank), on a heavy multi-house cast.

### 18.2 Workstream B — test seed (separate commit) — IMPLEMENTED 2026-07-03

### 18.3 Two constraints that shape the manual test flow

- **Time-travel to pre-summer to exercise the window.** deadline <= start (2026-06-01) and
  an open window needs `now < deadline`, so the sim clock must sit in late May to
  submit/build. Natural sequence: clock ~May 20 -> submit + build from preferences ->
  advance clock into summer -> test floating and edge cases.
- **Resolve the overlapping "Summer 2026" periods.** The base seed's `regular_school_year`
  Summer period overlaps the `s_summer2026` season period; with global periods this makes
  "active period" ambiguous and misroutes preferences. Verify the app's active-period
  resolution and ensure the `s_summer2026` period is the single unambiguous summer target
  (seed removes/avoids the conflicting base period). Ties into §16 audit task #1.
